# Agentic Cache Hierarchy Design

## 1. The problem and goal

Every CPU uses caches: small, fast memories that keep recently used data close to
the processor. Designing a cache is a trade-off. Larger and more associative caches
miss less often, but they are slower to access and cost more chip area. The best
design also depends on the program: a cache that works well for matrix code can
work poorly for code that follows pointers through memory.

**Goal:** design a two-level cache hierarchy (L1 and L2) that minimises the
average memory access time (AMAT) over a fixed set of benchmark workloads, while
staying within a total capacity budget.

**How it is measured:** AMAT in cycles, computed from the simulator's hit and miss
counts and a documented latency model. Lower is better. A design that exceeds the
capacity budget is rejected, however fast it is.

## 2. The simulator

- **Tool:** `pycachesim`, an open-source Python cache simulator with a fast C
  backend, called directly from Python with no GUI.
- **What goes in:** a cache configuration (L1 and L2 size, associativity, block
  size, replacement policy) and a set of memory-access traces. The traces are
  generated by my own deterministic Python code from fixed access patterns: naive
  matrix multiply, blocked matrix multiply, a 2D stencil, and a linked-list
  traversal.
- **What comes out:** hit and miss counts per cache level and per workload, from
  which AMAT is computed. A simple latency model makes hit time grow with cache
  size and associativity, so bigger is not automatically better.
- **Could it run without the AI?** Yes. It is a plain Python function: the same
  configuration always gives exactly the same result, one evaluation takes
  seconds, and it can be unit-tested with small traces whose miss counts can be
  worked out by hand.

## 3. The agent's role

The agent works in a loop: it proposes a configuration with a hypothesis, runs the
simulator, reads the per-workload results, and adjusts.

**What the model decides that a for loop could not:** the design space is large
(sizes, associativities, block sizes and policies at two levels), and each
simulator evaluation is limited by a budget. A for loop either tries everything,
which is too expensive, or samples blindly. The agent instead reads *why* a
design performed as it did, for example that the stencil workload suffers
conflict misses, which suggests raising L1 associativity rather than size, and
that the linked-list workload gains little from larger blocks. It uses that
diagnosis to choose the next experiment and to balance conflicting workloads.

**The for-loop test:** I will compare the agent against grid search and random
search given the same number of evaluations. The agent earns its place only if it
reaches a lower AMAT, or the same AMAT with fewer evaluations.

**Human checkpoints:** I set the goal, budget and evaluation limit; I approve or
redirect the search mid-run; and I verify the final design by re-running it and
checking that the results make sense.

## 4. In plain language

A computer's processor is much faster than its main memory, so it keeps a small
"desk drawer" of recently used data close by, called a cache. A bigger drawer
holds more but takes longer to search, and space on the chip is limited. Different
programs use memory in different ways, so the best drawer design depends on the
job. This project builds an AI assistant that designs the drawer: it suggests a
design, a reliable simulator tests it, the assistant reads the results and
explains what went wrong, and it tries again until it finds a fast design that
fits the space limit. The simulator does all the calculation; the AI only decides
what to try next.
